## 수행 범위

이번 기록은 공개 문서·코드와 **기존 대조 기록을 읽고 제공한 검토 의견**이다. 새 DART 조회는 수행하지 않았다고 명시되어 있다. 아래 금액·페이지는 기존 기록을 참조한 것이며, b가 실제 PDF부터 새로 독립 확인한 정답이라고 기록하지 않는다.

안드로이드 Chrome 환경이 기재되어 있으나, 업무별 실제 조작·화면 결과·도움·실행 로그는 제출 기록에서 확인되지 않는다. 모바일에서 “확인할 필요가 있다”, “확인하겠다”는 의견을 실제 동작 통과로 바꾸지 않는다. 28분은 보고된 검토 세션 길이이며 업무 성공률이나 전후 작업시간 개선의 근거가 아니다.

## 업무 카드별 의견 요약

아래는 제공된 의견의 요약이다. 직접 인용문이나 녹취록으로 표현하지 않는다. [사용한 업무 카드](finance-peer-review.md)와 [기존 세션 a의 원문 대조](session-a-20261107.md)를 함께 참조한다.

### 1. 출처 확인

보고서에 옮길 금액은 다른 사람이 같은 자료에서 같은 수치를 찾을 수 있도록 표·행·열까지 확인할 수 있어야 한다. 기존 기록의 대상은 삼성전자 2024년 3분기 영문 IR PDF p.34 연결 손익계산서의 Revenue 행, 2024년 3개월 KRW 열이다. 금액은 79,098,731백만 원, 기간은 2024년 7~9월이며 같은 행의 누적 열과 구분해야 한다.

추출 수치와 출처를 한곳에 모으는 구성은 검토에 도움이 될 것으로 보았다. 원문을 열 때 표 제목·열 머리글을 함께 볼 수 있어야 하며, 모바일에서 숫자를 확대할 때 기간·단위를 놓치지 않는지 확인할 필요가 있다는 의견이다.

### 2. 정상 비교

반기 보고서라도 선택한 열이 4~6월이면 2분기 단독 실적이다. 문서 제목과 실제 비교 기간을 구분하고 두 금액 가까이에 기간을 표시하는 것이 중요하다는 의견이다.

|구분|기존 기록의 금액|비교 기간|범위|
|---|---:|---|---|
|A|79,098,731백만 원|2024년 7~9월, 3개월|연결|
|B|74,068,302백만 원|2024년 4~6월, 3개월|연결|

같은 기업·항목·범위·통화·단위이고 인접한 분기라는 조건에서 `(79,098,731 ÷ 74,068,302 − 1) × 100 = 6.7916%`(소수점 넷째 자리)다. 보고서에는 “2024년 3분기 연결 매출의 전분기 대비 증가율”처럼 기준을 붙이고, 저장·공유 결과에도 두 금액·기간·연결 여부·출처를 남기겠다는 의견이다.

### 3. 기간이 다를 때의 판단

3분기 단독 매출과 상반기 누적 매출의 비율을 전분기 증가율로 사용하지 않겠다는 판단이다. B의 145,983,903백만 원은 1~6월 6개월 실적이며, 2분기 단독 실적으로 읽지 않도록 표시해야 한다.

계산 보류와 `0%`를 구분하고 성장률 미계산을 분명하게 보여 주는 것이 적절하다는 의견이다. “B를 2024년 4~6월 단독 분기로 변경한 뒤 다시 비교”와 같은 다음 행동 안내를 제안했다. 누적 차감도 기업·계정·범위·통화와 누적 시작일을 먼저 맞춰야 한다고 보았다.

### 4. 연결과 별도가 섞였을 때의 판단

같은 3개월이어도 연결과 별도가 섞이면 비교를 중지하고 범위를 맞추겠다는 판단이다. 기존 기록의 B 별도 매출 53,734,118백만 원을 A 연결 매출과 같은 범위의 실적 변화로 설명할 수 없다고 보았다.

개인 확인 표시를 눌러도 자동 보류가 유지되는 구조가 적절하며, 사용자가 보았다는 표시와 비교 조건 충족 판정을 혼동하지 않도록 문구가 명확해야 한다는 의견이다. 이 기록은 b가 해당 버튼을 직접 눌러 재검증했다는 실행 기록이 아니다.

### 5. IR와 DART 대조

IR의 백만 원과 DART의 원 단위를 맞춘 뒤 조건을 확인해야 한다는 의견이다. `79,098,731 × 1,000,000 = 79,098,731,000,000원`이며, 환산 금액 외에 기업·보고서·연도·범위·계정·단독/누적·원본 필드를 함께 봐야 한다.

조건이 같은 후보가 두 개라면 금액이 같더라도 임의로 하나를 고르지 않고, 근거 행이 명확해질 때까지 보류하겠다는 의견이다. 새 조회와 기존 기록을 구분하고, 연결/별도 중 요청 정보에 의존하는 부분과 응답에서 독립 확인한 부분을 나눠 설명할 필요가 있다고 지적했다. **이번 검토에서 새 DART 조회는 수행하지 않았다.**

### 6. 검토 흐름

금액·단위·쪽수·행·열·실제 기간을 함께 보여 주고 보류 사유에서 관련 조건으로 이동하는 방향을 긍정적으로 보았다. 확대 창은 추출 수치·출처 정보이며 실제 원문 확인은 발행사 PDF에서 이어진다는 점을 분명하게 전달할 필요가 있다는 의견이다.

모바일에서 금액·기간·단위가 함께 보이는지, 닫기 후 원래 항목으로 돌아오는지, 이동한 설정이 눈에 들어오는지는 실제 수행으로 확인하겠다는 의견이다. 전후 작업시간 비교에는 같은 업무의 실제 수행 기록이 필요하다고 보았다.

## 종합 의견과 후속 검토 과제

원문과 비교 기준을 함께 확인하고, 조건이 다르면 성장률을 내보내지 않는 구조가 유용할 것으로 보았다. 자료 정정 여부·비교 목적을 재확인하고 결과를 받은 사람이 원문과 계산 조건을 다시 찾을 수 있어야 한다는 의견이다.

|후속 과제|아직 확보할 결과|
|---|---|
|비교 기준의 가독성|모바일 A/B 금액 가까이 실제 기간·범위·단위를 읽을 수 있는지 직접 수행 기록|
|보류 이후 조치|원인을 이해하고 적절한 설정을 찾을 수 있는지, 도움·막힌 지점 기록|
|결과의 재확인|내려받은 CSV나 공유 결과에서 원문과 조건을 다시 찾는 실제 수행 기록|

위 과제는 제안이며 새 구현이나 개선 효과를 확인한 결과가 아니다. [기존 UI 보완](../feedback-followup-20261108.md)은 b의 의견 수집 전에 배포된 변경으로, b의 의견 때문에 구현했다고 소급해 표현하지 않는다.

## 코드와의 대조 — AI 확인, 참여자 수행과 별도

`49627e9` 기준으로 AI가 코드 읽기를 통해 확인했다. 새 테스트나 API 실행 결과가 아니다.

- [`dart.py`](../../quarterguard/dart.py)의 `fetch`는 응답의 기업 코드·사업연도·보고서 코드를 요청과 대조한다. `scope`는 요청 인자에서 가져오며 `scope_basis='request_fs_div'`로 표시한다.
- [`live_verification.py`](../../quarterguard/live_verification.py)의 `check_dart_rows`는 조건에 맞는 후보가 정확히 하나일 때만 금액을 읽는다. 이 단계에서 scope가 일치한다는 것은 응답에서 범위를 독립 인증했다는 뜻이 아니다.
- [`core.py`](../../quarterguard/core.py)의 `Fact.amount`는 `Decimal(value) * scale`로 정규화한다.
- [`providers.js`](../../web/providers.js)는 이미 “연결·별도 범위는 요청한 fs_div 기준”이라는 안내와 실제 요청/캐시 구분을 제공한다. [기존 DART 검토 자료](../code-review-kit/03-dart-ir.md)에도 이 한계가 있다. b의 의견은 이를 재확인한 것으로, 새 버그 발견·수정이라고 표현하지 않는다.
